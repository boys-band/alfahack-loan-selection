# Сквозные браузерные сценарии

`e2e-real/` проверяет production frontend → gateway → шесть Java API → настоящую PostgreSQL. Отдельный `playwright.real.config.ts` не запускает Vite/MSW, блокирует Service Worker и проверяет `MOCK_API=false`. `e2e/` остается отдельным набором со стабами для управляемых часов, таймеров, сбоя worker и исправления счета.

## Запуск

Из корня checkout с общим Compose:

```bash
docker compose -p alfa-local up -d --wait
npm --prefix frontend ci
npm --prefix frontend run test-e2e:real
npm --prefix frontend run test-e2e
```

Административная публикация меняет текущую версию продукта в постоянной БД, поэтому `admin-products.spec.ts` пропускается в обычном полном real-наборе. Запускайте её в отдельном Compose-проекте и volume:

```bash
docker compose -p alfa-admin-e2e -f compose.yaml -f frontend/e2e-real/compose.admin.yaml up --build -d --wait --wait-timeout 180
E2E_BASE_URL=http://localhost:18082 E2E_ADMIN_ISOLATED=1 npm --prefix frontend run test-e2e:real -- admin-products.spec.ts
docker compose -p alfa-admin-e2e -f compose.yaml -f frontend/e2e-real/compose.admin.yaml down
```

Порт можно изменить через `ADMIN_E2E_PORT` вместе с `E2E_BASE_URL`. Этот проект не использует volume `alfa-local` и не влияет на ожидания equipment v1/22% в существующих real-тестах. После `down` его собственный volume сохраняется; сценарий читает текущую версию перед запуском и допускает повторный прогон. Полный legacy real-набор запускайте на чистом `alfa-local` или другом проекте с исходным seed.

Node.js 22.22.1. Используется `/usr/bin/google-chrome`; при его отсутствии установить Chromium через `npx playwright install chromium` из `frontend/`. Другой браузер: `PLAYWRIGHT_CHROMIUM_EXECUTABLE=/path/to/chromium`. Адрес и демотокены можно переопределить через `E2E_BASE_URL`, `E2E_CUSTOMER_TOKEN`, `E2E_STAFF_TOKEN`, `E2E_ADMIN_TOKEN`; по умолчанию `http://localhost:8080`, `demo-customer-only`, `demo-staff-only`, `demo-product-admin-only`.

Набор рассчитан на синтетический seed проекта и демопользователя, которому доступны пять компаний. Сценарий ручного риска 550 использует дату регистрации «Демо Ручной анализ» из seed; при смене календарного возраста компании ожидаемый маршрут нужно пересмотреть вместе с фикстурой. Тесты не меняют часы backend и не добавляют тестовые параметры в публичный протокол.

Административный сценарий `admin-products.spec.ts` публикует новую версию equipment через UI, проводит уже созданный черновик до `OFFER_READY` с прежним продуктом и проверяет 412 во втором admin-окне. В mock-наборе отдельно проверяются потерянный ответ и точный повтор, а также сохранение ввода после 412. Публикация добавляет неизменяемую версию в тестовую БД; сценарий использует equipment, чтобы не менять ожидаемые условия основного пути working-capital.

## Изоляция и диагностика

Один worker Playwright, новый browser context на каждый тест, без автоматических retries. Подготовка выполняется через публичные API, бизнес-действия — через формы; прямых изменений БД и внутренних API в тестах нет. В тестах конкурентных запросов используются публичные API и проверяется финальный результат в браузере.

`loseReply` сначала получает успешный ответ настоящего API через `route.fetch()`, затем обрывает ответ браузеру. Повтор доходит до реального сервиса. Искусственные 429/409/503/401 инжектируются только на браузерной границе; это не доказательство отказоустойчивости самих серверов. Непрерывность worker после падения/lease и потерянный ответ зачисления отдельно покрыты интеграционными тестами applications.

Каждый тест ведет список своих заявок. После него незавершенные заявки отменяются через публичный API; завершенные заявки и неизменяемая история сохраняются. Чужие заявки и volume не очищаются. В список после прогона добавляются синтетические записи; staff-очередь не должна зависеть от их количества или порядка.

Артефакты разделены, чтобы наборы можно было запускать независимо:

- `test-results/real`, `playwright-report/real` — реальные API;
- `test-results/mock`, `playwright-report/mock` — стабы;
- JSON-снимки созданных заявок и ошибки JS прикладываются к каждому real-тесту;
- при ошибке сохраняются screenshot и trace, для успешного полного пути — screenshot выдачи.

```bash
cd frontend
npx playwright show-report playwright-report/real
# Один сценарий:
npm run test-e2e:real -- --grep 'lost sign'
```

Проверки финансовых дат/сбоев со стабами и реальная интеграция намеренно имеют разные команды и отчеты. Охват сценариев не означает процент покрытия исходного кода.

## Staff registry

`staff-registry.spec.ts` проверяет AUTO OFFER_READY → staff-фильтр/reload/история/версия → клиент принимает/подписывает → staff-договор/DISBURSED; второй сценарий проверяет ручное одобрение, исчезновение формы и MANUAL-фильтр. Запускать на изолированном профиле через `python scripts/staff_registry_stack.py --project alfa-staff-it-review --port 18085`, затем `E2E_BASE_URL=http://127.0.0.1:18085 npm --prefix frontend run test-e2e:real`.

## Проверка создания и архивирования (25.10.2026)

Отдельный проект `alfa-admin-e2e` поднят командой `docker compose -p alfa-admin-e2e -f compose.yaml -f frontend/e2e-real/compose.admin.yaml up --build -d --wait --wait-timeout 180`; все сервисы и gateway прошли healthcheck. Запуск двух тестов `admin-products.spec.ts` в локальном Node 22/Chrome-образе с `--network=container:alfa-admin-e2e-gateway-1` и `E2E_BASE_URL=http://localhost:8080 E2E_ADMIN_ISOLATED=1` завершился `2 passed`. Новый тест создаёт уникальную программу через UI, проводит заявку до подписания, архивирует её, проверяет прежний договор/подпись и завершение выдачи, продолжает ранний черновик и проверяет `409 PRODUCT_NOT_CURRENT` для новой заявки и смены продукта. Старый тест публикации v2 также прошёл.

При запуске браузера внутри Docker используйте `localhost` в сетевом пространстве gateway: HTTP-адрес `host.docker.internal` не считается браузером безопасным контекстом, и `crypto.randomUUID()` в клиенте недоступен. На хосте с установленным Node используйте опубликованный `http://localhost:18082`. После пересоздания frontend-контейнера в существующем проекте перезапустите gateway, чтобы nginx разрешил его новый IP: без этого первый повторный запуск получил `502` на `/config.js`. После перезапуска оба теста прошли. Тестовый volume изолирован; `down` без `-v` его сохраняет.

Полная прежняя real-регрессия прошла на отдельном чистом Compose-проекте `alfa-admin-regression`: `47 passed, 2 skipped` (оба изолированных admin-сценария), без retries. После неё оба seed-продукта архивированы через HTTP: клиентский список стал пустым, точная версия `1` обоих продуктов читается, `catalog /health/ready` вернул `200`.
