# Кредитный кабинет — frontend

Клиентская desktop SPA, рабочее место сотрудника и админ-панель условий кредитных продуктов на TypeScript 5.9.3, React 19.1.1, React Router 7.9.4 и Vite 7.1.12. Node.js 22.22.1; зависимости зафиксированы в `package-lock.json`, образ Node — тегом и digest в `Dockerfile`.

## Запуск

Из корня репозитория:

```bash
npm --prefix frontend ci
MOCK_API=true make -C frontend dev
```

Открыть `http://localhost:3000`. Вход: роль «Предприниматель», токен `demo-customer`; для сотрудника — роль «Сотрудник», `demo-staff`; для администратора — роль «Администратор», `demo-admin`. Эти значения действуют только в HTTP-стабе. Каталог → выбор продукта → черновик → сохранение → два согласия → отправка → предложение → принятие → полный договор → согласие на подпись → подтверждённая выдача. Первый запуск стаба в чистом профиле браузера начинает с пустого списка заявок.

Для настоящего gateway:

```bash
MOCK_API=false API_PROXY_TARGET=http://localhost:8080 make -C frontend dev
```

Демотокены настоящего API берутся из конфигурации сервисов; frontend их не задаёт. Dev-сервер проксирует `/api` на gateway, сохраняя same-origin для браузера. Browser API содержит только applications/catalog `/api/v2/*`, включая catalog admin API. Отдельного endpoint входа нет: доступ проверяется запросом компаний, staff-очереди или списка admin-продуктов.

Над формой входа показаны синтетические тестовые токены для каждой роли: в режиме стабов — значения из примера выше, при `MOCK_API=false` — стандартные значения локального Compose (`demo-customer-only`, `demo-staff-only`, `demo-product-admin-only`). На стенде с изменённым доступом токен нужно уточнить у организатора; подсказка не настраивает и не проверяет серверные права. Ошибки 401 и 403 объясняют непринятый токен и неподходящую роль, сетевой сбой и недоступность сервиса отображаются отдельно, без технического текста ответа. Поле остаётся парольным; ввод и смена роли очищают прежнюю ошибку, во время проверки форма заблокирована.

## Конфигурация и контейнер

| Переменная         | По умолчанию            | Назначение                                                    |
| ------------------ | ----------------------- | ------------------------------------------------------------- |
| `API_BASE_URL`     | `/api`                  | Same-origin префикс gateway; без домена, query и fragment     |
| `MOCK_API`         | `false`                 | Явное включение HTTP-стабов, с заметной отметкой в интерфейсе |
| `API_PROXY_TARGET` | `http://localhost:8080` | Только dev-сервер: адрес gateway для `/api`                   |
| `PORT`             | `3000`                  | Порт production HTTP-сервера                                  |

`.env.example` можно скопировать в `.env` для разработки. В production `/config.js` формируется сервером из env при запуске, отдаётся с `Cache-Control: no-store` и содержит только `API_BASE_URL`/`MOCK_API`. Пересборка для смены этих параметров не требуется. Токены хранятся в `sessionStorage`; их нет в URL и логах. Журналы разных демоличностей разделены по SHA-256 от роли и токена.

```bash
docker build -t alfa-frontend:local frontend
# Проверка образа в двух runtime-режимах (из frontend/):
# node scripts/smoke-container.mjs
# Демо на HTTP-стабах:
docker run --rm -p 127.0.0.1:3000:3000 -e MOCK_API=true alfa-frontend:local
# За настоящим gateway (моки выключены по умолчанию):
docker run --rm -p 127.0.0.1:3000:3000 -e API_BASE_URL=/api alfa-frontend:local
```

Второй вариант предполагает маршрутизацию `/api` в backend на общем gateway. Сам static-сервер не заменяет gateway. Контейнер работает от пользователя `node`, слушает `0.0.0.0:3000`. Прямые UI URL и reload используют SPA fallback. Отсутствующие assets и API-пути возвращают 404. Сборка полностью выполняется с контекстом `frontend/`, без чтения контрактов снаружи контекста.

## Реализованное поведение

- Все маршруты спецификации: продукты, компании, создание/список/карточка заявки, история, неизменяемые версии, полный договор, staff-очередь и дело. Cursor pagination без выдуманного общего количества.
- Все 26 UI-операций из OpenAPI. `src/api/generated.ts`, `contract/operations.json` и схемы зафиксированы в компоненте. AJV проверяет отправляемые DTO и ответы, включая nullable, enum, неизвестные поля и правила StaffReviewActionRequest.
- Администратор видит текущие и архивные версии продукта, редактирует поля `Product`, просматривает отличия и публикует новую неизменяемую версию с причиной. `If-Match` защищает от конкурентной правки; отдельный журнал admin-команд хранит точный запрос для повтора после потери ответа. При `412` форма сохраняется до явного подтверждения обновлённых условий. Существующие заявки, предложения и договоры не переписываются.
- На `/admin/products/new` администратор задаёт ID и условия новой программы, проверяет все итоговые поля и подтверждает немедленную публикацию v1. Список фильтрует активные, архивные и все программы. В активной карточке архивирование требует обоснование и подтверждение; архивная карточка сохраняет чтение истории и не предлагает публикацию. Журнал хранит создание, публикацию и архивирование отдельно, включая точные тело, путь, ключ, ETag и заголовки для повтора после reload.
- Все 15 статусов и оба reviewStage. Серверные availableActions, processing, technicalError, причины решений, оценённое предложение REQUESTED/COUNTER. Кредитные расчёты в интерфейсе не выполняются.
- Явное сохранение черновика; пустые числа остаются null, ноль допустим для финансов. При замене вложенного объекта сохраняются соседние значения. Несохранённые правки не затираются GET; уход и browser back требуют подтверждения.
- Журнал команд сохраняется до отправки. Повтор использует неизменные method/path/body или отсутствие тела/If-Match/Idempotency-Key. Двойной клик блокируется; после потери ответа сначала перечитываются сведения, затем пользователь повторяет исходную команду. 412 сохраняет форму и требует явного ознакомления перед новым намерением. 429/IDEMPOTENCY_IN_PROGRESS учитывают Retry-After.
- Ответ 202 подтверждает только приём. Старый receipt не применяется к карточке; результат берётся из нового GET. Незавершённая команда блокирует новое намерение по этой заявке. Ответы прежней карточки/сессии отбрасываются; GET не понижает version.
- Опрос без пересечений: 2 с при обработке, 15 с при ожидании человека, backoff до 15 с и Retry-After. Скрытая вкладка приостанавливает регулярный опрос; focus обновляет данные. Финальные состояния не опрашиваются регулярно.
- INFO/OFFER/SIGNATURE: абсолютный срок в МСК, обратный отсчёт со смещением по HTTP Date, блокировка и обновление на границе. Подпись использует отдельный signBy, а не expiresAt предложения.
- Полный text/plain документ экранируется и сохраняет переносы. Новые версия/хеш сбрасывают согласие. Подпись отправляет ID/версию/хеш показанного документа. Отмена после 202 не объявляется окончательной до серверного исхода.
- Исправление своего счёта в SIGNED сохраняет договор. DISBURSED показывает подтверждённую операцию. Staff APPROVE/REJECT/REQUEST_INFO/AMEND_DATA используют публичный DTO с nullable полями; автора и ID действия назначает сервер. Без оценки/подтверждённых фактов APPROVE отсутствует.
- Loading/empty/error, сохранение последних данных при сбое, привязка ошибок к полям; 401 с безопасным возвратом к маршруту, 403/404. Keyboard focus, нативные диалоги и Escape.

Ошибки продуктовых лимитов показывают русское название поля вместо JSON Pointer. Диапазон из `errors[].message` applications сохраняется; прежнее `Outside current product limits` переводится отдельно для суммы и срока, поэтому обновленный интерфейс работает и с прежним backend. При ошибках полей технический `detail` заменяется предложением проверить форму; отладочные коды и RequestId не выводятся в интерфейс. Поля формы сохраняются. Подтверждение нового намерения требуется при конфликте версии или неоднозначном исходе команды; отклоненная валидацией правка черновика допускает немедленное исправление.

Подтверждение отправки, история и карточки показывают сведения с русскими подписями, без JSON-дампов запросов и ответов. Дополнительные сведения и согласия сохранены в интерфейсе; у сотрудника факты источников и оценённые условия представлены отдельно. Технические коды этапов, счетчики повторов и хеш документа не отображаются. RequestId, ETag, ключи повторов и хеш подписи продолжают использоваться внутри API-клиента. Полный текст договора остаётся доступен.

После подтверждённого `422 VALIDATION_ERROR` на создание или сохранение черновика отклоненная команда удаляется из журнала. Ошибка и введенные значения остаются в форме, кнопка сохранения доступна; исправленные данные отправляются с новым Idempotency-Key на той же странице и для той же заявки. Потеря ответа, конфликты идемпотентности/версии и неоднозначные ответы сохраняют исходную команду и прежние правила восстановления.

Представление решения учитывает роль. Предприниматель видит общий отказ либо условия предложения без банковских причин, баллов, факторов риска, результатов внутренних проверок и обоснований сотрудника. В истории клиента используются понятные названия событий вместо внутренних комментариев; архивные версии сохраняют его сведения и согласия. Сотрудник видит полные причины, оценку, проверки и уточнения. Это правила отображения экранов; схемы публичного API остаются общими для обеих ролей.

В рабочем месте сотрудника исходные и подтверждённые факты сопоставляются в таблице: различия помечаются «Уточнено», отсутствующие значения — «Нет сведений». Варианты кредита сравниваются по сумме, сроку, ставке, платежу, риску, нагрузке, свободному потоку и допустимости; выбранный сервером вариант отмечен. Диаграмма факторов показывает серверные баллы, включая нулевые, с доступными текстовыми подписями. Она не пересчитывает решение и не показывает вероятность одобрения.

## HTTP-стабы

MSW 2.11.6 перехватывает реальные browser HTTP-запросы только в mock mode. `src/mocks/bank.ts` — отдельный тестовый сервер состояний с фикстурами из согласованных примеров. Он хранит версии, историю, договоры и идемпотентные receipts, моделирует задания и проверяет DTO по тем же схемам. В обычном режиме mock chunk не загружается. У стаба нет подключений к БД.

Для воспроизведения ветвей в devtools при включённых моках:

```js
// Влияет только на новые заявки стаба:
window.__MOCK__.scenario = 'counteroffer';
// approved / counteroffer / declined / validation-info / verification-info /
// decision-info / manual / unconfirmed / payout / technical

// Подготовить дело для staff-очереди:
window.__MOCK__.seed('manual', 'MANUAL_REVIEW');
// Аналогично: seed('unconfirmed', 'MANUAL_REVIEW') — без права APPROVE.
// После этого обновить очередь либо сменить роль через выход/вход.

// Одноразовый технический HTTP-сбой:
window.__MOCK__.nextFault = { operation: 'updateDraft', lost: true };
// Также status: 412/422/429/503, code, delay (мс).

// Очистить синтетический сервер:
window.__MOCK__.reset();
```

Состояние стаба хранится в `localStorage` (`alfa.mock.bank`) и переживает reload/смену роли в одном браузере. Это удобство демо, без гарантии синхронизации независимых вкладок. Часы и длительность шага управляются тестами через MockBank; это не параметры публичного API. Результаты скоринга/платежей в стабе — фиксированные синтетические примеры, а не банковский расчёт. Основной ручной happy path соответствует примеру: 1 000 000 ₽, 12 мес., выручка 1 000 000 ₽, расходы 500 000 ₽, текущие платежи 20 000 ₽.
