# Контракты v2

Шесть OpenAPI 3.1.0 спецификаций (`info.version=2.0.0`), общие [JSON Schema](schemas.yaml), синтетические [примеры](examples). Основание — [бизнес-модель](../docs/application-state-model.md); точные guards — [workflow](../docs/workflow.md). Предыдущие не реализованные контракты v1 заменены: актуальная реализация использует `/v2`.

## API и доступ

Публикация условий продуктов идет через `/v2/admin/products*` в catalog с отдельным `AdminBearer`. CustomerBearer, StaffBearer и InternalBearer не разрешают эту команду. Административный ETag — SHA-256 канонического JSON всего ответа `AdminProduct`, в кавычках; он относится к текущему указателю и истории версий. `POST /versions` с `If-Match` и `Idempotency-Key` возвращает `201`; точный повтор возвращает сохраненные `201`, тело и ETag, даже если позднее опубликована следующая версия. Новый ключ со старым ETag дает `412 VERSION_CONFLICT`.

Создание программы: `POST /v2/admin/products` с `CreateAdminProductRequest` и `Idempotency-Key` возвращает активную версию `"1"` и `201`. ID задается один раз; повтор с новым ключом и теми же исходными полями, включая `reason`, возвращает текущий `AdminProduct` и `200`, иной запрос на занятый ID — `409 PRODUCT_ALREADY_EXISTS`. Архивирование: `POST /v2/admin/products/{productId}/archive` с `{reason}`, `If-Match` и `Idempotency-Key` возвращает `200` и `active=false`. Архив не удаляет версии; публикация следующей версии запрещена с `409 PRODUCT_ARCHIVED`. Точный повтор любой команды возвращает сохраненные статус, тело и ETag, даже после последующих изменений; другой отпечаток под тем же ключом дает `409 IDEMPOTENCY_CONFLICT`. Устаревший `If-Match` дает `412 VERSION_CONFLICT`, отсутствующий — `428`. Причина содержит 10–2000 Unicode-символов; неизвестные поля запрещены. `DELETE` для физического удаления программы нет.

| Контракт | Публичные ресурсы через `/api` | Внутренние ресурсы |
| --- | --- | --- |
| applications.yaml | `/v2/companies`, `/v2/applications`, `/v2/staff/*` | Те же пути, доступ проверяет applications |
| catalog.yaml | `/v2/products`, `/v2/admin/products*` для администратора | `/v2/products` |
| verification.yaml | Нет | `/v2/verifications` |
| decision.yaml | Нет | `/v2/decisions`, `/v2/manual-reviews` и действия |
| agreements.yaml | Нет | `/v2/agreements`, `sign`, `close` |
| disbursement.yaml | Нет | `/v2/company-accounts`, `/v2/payout-checks`, `/v2/disbursements`, поиск `by-operation` |

`CustomerBearer` и `StaffBearer` — разные настроенные демотокены. Клиент видит свои ресурсы, сотрудник — банковскую очередь и заявку для рассмотрения. Сотрудник не получает право принимать предложение/подписывать за клиента. Клиент не получает доступ к staff API. Личности и роль устанавливает applications из конфигурации токенов. Внутренний `InternalBearer` принимают только внутренние операции и catalog. Чужой клиентский ресурс — `404`, недостаточная роль — `403`.

## HTTP, конкуренция и повторы

Черновик перед первой отправкой должен использовать текущую активную версию продукта. PATCH черновика читает актуальный продукт и проверяет переданные/сохранённые значения по его ограничениям; при успехе обновляет снимок программы, при 422 не меняет черновик. Submit старой версии возвращает `409 PRODUCT_NOT_CURRENT` без создания версии данных; клиент предлагает проверить новые условия и сохранить черновик. Недоступность catalog не разрешает отправку по старым условиям. Уже отправленные версии данных, предложения и договоры сохраняют свои снимки. Успешные повторы с прежним ключом возвращают исходный ответ до повторной проверки catalog.

- JSON UTF-8, camelCase, неизвестные поля запрещены. Nullable поля ответа всегда присутствуют. Деньги — целые рубли, ставки/отношения — базисные пункты. UUID canonical lowercase, время UTC с `Z`.
- `X-Request-Id` — UUID трассировки, создается при отсутствии, передается дальше и возвращается в каждом ответе.
- POST/PATCH требуют `Idempotency-Key` (8–128 символов `A-Za-z0-9:_.-`). PATCH/команды конкретной заявки дополнительно требуют `If-Match`. Создание черновика не требует `If-Match`.
- ETag — кавычки и SHA-256 канонического JSON текущей заявки (UTF-8, ключи отсортированы, без пробелов, `ensure_ascii=false`). Клиент передает его дословно, не выводит из `version`. Вычисление доступности действий после deadline может изменить ETag без сохраненного изменения version. Ответы заявки используют `Cache-Control: no-store`.
- В одной транзакционной блокировке приложения проверяются текущие статус/версия данных/предложение и deadline. До выполнения команды сравнивается ETag представления на текущее время. Устаревший ETag — `412`, отсутствие — `428`. Если проверка deadline обнаружила истечение, действие запрещено; таймер/обработка срока доводят состояние до EXPIRED, с разрешением гонки подписи через agreements.
- Порядок: аутентификация/владелец/роль → сохраненный идемпотентный ответ → текущие guards/ETag → изменение. Повтор успешной команды со старым ETag воспроизводит исходные статус/тело/ETag; затем клиент перечитывает текущую заявку.
- Отпечаток запроса: метод, конкретный путь, каноническое тело и If-Match, когда требуется. Отсутствующее тело отличается от `{}`, отсутствующее поле от null. Тот же ключ и другой отпечаток — `409 IDEMPOTENCY_CONFLICT`.
- Уникальность записи повтора: `(caller, method, path, key)`. Успешный ответ и изменение ресурса фиксируются атомарно. Хранение публичных ключей не менее 24 часов, внутренних — весь срок хранения заявки. Ошибки не кэшируются как успех. Конкурентный одинаковый запрос ждет первый либо получает `409 IDEMPOTENCY_IN_PROGRESS` с `Retry-After`.
- Создание ресурса — `201`; повтор того же ключа — прежний статус/тело; другой ключ с тем же бизнес-ресурсом и входом — `200`. Несовпадающий вход при прежнем бизнес-ключе — `409`. Внутренние sign/close также возвращают `200`.
- Команды процесса — `202`: намерение сохранено, окончательный исход еще не обещан. Cancel вне гонки с подписью может закончиться сразу (`200`). GET безопасен и не меняет бизнес-состояние.

Ключ этапа включает `applicationId`, `dataVersion`, шаг и конкретный ID запуска. Примеры: `enrich:<app>:<dataVersion>`, `score:...`, `manual:<case>:<actionId>`, `agreement:<app>:<dataVersion>`, `sign:<agreement>:<documentVersion>`, `payout-check:<app>:<dataVersion>:<payoutVersion>`, `disburse:<operationId>`. Закрытие ресурсов имеет отдельный сохраненный ключ. При повторе запрос не пересобирается из текущего состояния.

## Версии и команды

`version` — версия агрегата, `dataVersion` — версия исходных данных: 0 в черновике, 1 после первой отправки, затем +1 при изменении. Первая отправка сохраняет согласия и серверное acceptedAt, последующие версии наследуют действующие согласия. Клиент не задает время, автора, скоринг, состояние или сумму выдачи.

| Команда applications | Тело | Источник → результат принятой команды |
| --- | --- | --- |
| PATCH заявки | UpdateDraftRequest | Только DRAFT, version +1 |
| submit | SubmitRequest: два true-согласия | DRAFT → SUBMITTED, dataVersion=1 |
| provide-info | informationRequestId + changes | NEEDS_INFO → SUBMITTED, новая версия |
| change-terms | ChangeTermsRequest | OFFER_READY → VALIDATION, новая версия и закрытие прежнего предложения |
| accept-offer | offerId + offerVersion + dataVersion | OFFER_READY → OFFER_ACCEPTED |
| sign | agreementId + documentVersion + documentSha256 + consent=true | AWAITING_SIGNATURE до подтверждения → SIGNED |
| cancel | reason | До подписания; в AWAITING_SIGNATURE исход сверяется с договором |
| payout-account | settlementAccountId | Только SIGNED; payoutVersion +1 и новая проверка |
| retry-processing | Без тела | Приостановленный этап возобновляется в том же бизнес-состоянии |
| staff/.../manual-review/actions | action + reason + termsId/requirements/changes/factsResolution | Только актуальная MANUAL_REVIEW; сотрудник/ID действия устанавливаются сервером |

Черновик допускает null в параметрах и отдельных финансовых показателях. PATCH: отсутствие поля не меняет его, null очищает; вложенные объекты заменяются целиком. В полной версии обязательны все параметры/финансы без null. `DataChanges` не содержит null: меняет только переданные поля, additionalInfo заменяет целиком. ProductId и productVersion меняются только вместе. Change-terms требует хотя бы одно фактическое изменение суммы/срока/продукта; пустое или неизменившееся дополнение/уточнение — `422`.

InformationRequest хранит конкретные JSON Pointer в requirements[].path, источник и срок. Ответ содержит запрошенные поля и может исправить связанные финансовые показатели; срок и ID дозапроса проверяются. Staff action: обоснование от 10 символов; APPROVE выбирает termsId из актуальной завершенной оценки, REQUEST_INFO имеет непустые requirements, AMEND_DATA — changes и/или factsResolution. Неиспользуемые nullable поля передаются как null, requirements — []. Уточнение фактов становится аудируемой staffAttestation новой версии, не меняет старый результат.

## Владение результатами и guards

`GET /v2/staff/applications` — отдельный read-only реестр для StaffBearer, все клиенты и статусы, включая DRAFT и автоматическое одобрение. Клиентский `GET /v2/applications` по-прежнему ограничен владельцем. Параметры `status` и `approvalType=AUTO|MANUAL` комбинируются через AND. Тип одобрения определяется только текущим APPROVED decision текущей dataVersion; дальнейшие статусы сохраняют этот тип, старые версии не классифицируют новую. Пагинация по `(created_at DESC,id DESC)`, limit 1–100 (20 по умолчанию), выборка limit+1. Новый непрозрачный staff-cursor связан с нормализованными фильтрами; испорченный cursor или другие фильтры — 422 VALIDATION_ERROR. Формат клиентского курсора не меняется. Это живой список без общего snapshot между страницами; новые записи сверху видны после возврата к первой. Ответ — ApplicationPage, Cache-Control: no-store, X-Request-Id. Реестр не дает права выполнять клиентские команды или обходить guards ручного workflow.

- Verification: один результат на `(applicationId, dataVersion)`. COMPLETE означает полные подтвержденные facts; rawFacts сохраняют исходный ответ. NEEDS_INFO и MANUAL_REVIEW не являются кредитным отказом.
- Decision: один AUTO и при необходимости один итоговый MANUAL на версию. Подтвержденные факты обязательны для оценки. `evaluatedTerms` хранят расчеты каждого кандидата; selectedTermsId и предложение относятся к действительно оцененному кандидату. Offer выдается только при APPROVED. ManualReviewCase один на версию; действие разрешает дело либо закрывает его с сохранением аудита.
- Нельзя одобрить ручное дело без текущего assessment и подтвержденных фактов; сотрудник в этом случае уточняет данные новой версией. REJECT с обоснованием допускается и без оценки, APPROVE — никогда. Одобрение не обходит стоп-правила. FactsResolution ссылается на verificationId своего дела; возраст бизнеса пересчитывается из подтвержденной даты регистрации на новый asOf.
- Agreement: один на версию данных; принятое предложение и документ неизменяемы, documentVersion=1 в этой поставке. READY → SIGNED либо CLOSED, без обратного перехода. SHA-256 считается от точных UTF-8 байт content. signBy проверяется на сервере договора; прежний expiresAt предложения после принятия не ограничивает подпись. Close уже закрытого договора с новым ключом возвращает его фактическую прежнюю closureReason, не перезаписывает ее. Close подписанного договора дает AGREEMENT_ALREADY_SIGNED.
- PayoutCheck: один на `(applicationId, dataVersion, payoutVersion)`, сохраняет все реквизиты и READY/NEEDS_CORRECTION. Последнее — бизнес-ожидание в SIGNED. Перед выдачей проверяются подписанный договор, совпадение всех ID/версий и успешный payout-check; сумма только из договора.
- Disbursement: отдельные уникальности applicationId, agreementId, operationId, одна credit entry. После неизвестного результата выполняется GET by-operation, затем при необходимости повтор с тем же operationId/ключом/телом. `404` не разрешает создать новую операцию.
- После отмены или смены версии поздний результат не двигает заявку. В гонке sign/close источник истины — атомарное состояние договора. Подписанный договор и результат выдачи сверяются при восстановлении.

## Ошибки

`application/problem+json`, схема Problem с code/requestId/errors[].path. Неверный JSON — `400 MALFORMED_JSON`; поля/типы/consent — `422 VALIDATION_ERROR`; чужие версии/связи — `422 SNAPSHOT_MISMATCH`; недоступный источник — `503 DEPENDENCY_UNAVAILABLE`. Успешный бизнес-отказ возвращается в DecisionResult с REJECTED.

`409`: INVALID_STATE, IDEMPOTENCY_CONFLICT, IDEMPOTENCY_IN_PROGRESS, DEADLINE_EXPIRED, OFFER_NOT_CURRENT, PRODUCT_NOT_CURRENT, DOCUMENT_MISMATCH, SIGNER_MISMATCH, AGREEMENT_CLOSED, AGREEMENT_ALREADY_SIGNED, AGREEMENT_NOT_SIGNED, SCORING_REQUIRED, PAYOUT_NOT_READY, OPERATION_IN_PROGRESS. `412 VERSION_CONFLICT`, `428 PRECONDITION_REQUIRED`, `401 UNAUTHENTICATED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `429 RATE_LIMITED`, `500 INTERNAL_ERROR`. Если срок восстановления известен, вернуть Retry-After в секундах; никаких stack trace/секретов.

Неполные/противоречивые сведения после отправки оформляются NEEDS_INFO, а не технической ошибкой. Сетевая ошибка сохраняет status/reviewStage и заполняет technicalError; повторяемость определена в архитектуре. AGREEMENT_CLOSED/AGREEMENT_ALREADY_SIGNED/DEADLINE_EXPIRED при подписи или закрытии требуют GET договора и разрешения гонки, а не автоматической фиксации технического отказа.

## Проверка и изменение контракта

`python scripts/validate_contracts.py` после установки requirements.txt: OpenAPI, ссылки, схемы, HTTP-примеры, seed и соответствие enum бизнес-модели. Реальные переходы/гонки проверяются интеграционными тестами при реализации.

Примеры содержат operationId, запрос/параметры и ответ. Они являются сценариями для стабов; не означают готовую реализацию. Коллекция requests.http предназначена для ручной проверки после запуска сервисов. Несовместимое последующее изменение оформляется новой версией API; меняются вместе схема, примеры и задания исполнителям.
