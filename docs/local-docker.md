# Локальный запуск и пользовательские сценарии

Полное окружение находится в `compose.yaml`: gateway Nginx, frontend React/TypeScript, шесть Java 21 API, отдельный applications worker и PostgreSQL с шестью БД. Только gateway публикует порт хоста: `127.0.0.1:8080`. Frontend работает с настоящими API (`MOCK_API=false`); источники проверки и зачисление используют предусмотренные проектом синтетические данные.

## Запуск

Из корня checkout с этим Compose. Java-образы собираются только с локальным дистрибутивом Gradle из `gradle-dist/` ([подробнее](../gradle-dist/README.md)):

```bash
curl -fL -o gradle-dist/gradle-8.14.3-bin.zip https://services.gradle.org/distributions/gradle-8.14.3-bin.zip
docker compose -p alfa-local up --build -d --wait --wait-timeout 180
docker compose -p alfa-local ps
```

Java, Node.js и PostgreSQL на хосте не нужны. Первая сборка загружает зависимости из интернета; на Linux для сборки задан `network: host` из-за DNS-сбоев bridge-сети в локальной среде.

Общий bootstrap применяет неизмененные `001_initial.sql` и seed. Одноразовый контейнер `migrate` применяет все следующие номерные миграции в порядке имени, включая `002_*` и catalog `003_program_lifecycle.sql`, транзакционно от NOLOGIN-владельцев схем. Он проверяет checksum и безопасно пропускает уже примененные миграции; пустой набор следующих миграций допустим. API используют только роли `*_app` с DML. Worker начинает работу после готовности всех API. Успешное завершение `migrate` со статусом `Exited (0)` нормально.

Открыть **http://localhost:8080**. Вход по адресу `/demo-access`:

| Роль | Демотокен |
| --- | --- |
| Предприниматель | `demo-customer-only` |
| Сотрудник | `demo-staff-only` |
| Администратор условий | `demo-product-admin-only` |

Токены `demo-customer` / `demo-staff` из mock-демо здесь не подходят. Для параллельной работы двух ролей используйте разные профили браузера или обычное и приватное окна.

## Редактирование условий продукта

Войти администратором и открыть `/admin/products`. Выбрать продукт, изменить разрешённые поля, заполнить причину и подтвердить публикацию. Перед отправкой UI показывает отличия. Новая версия сразу становится текущей в клиентском каталоге; старые версии доступны по точному номеру и остаются в существующих снимках отправленных заявок, предложениях и договорах. Неотправленный черновик нужно проверить и сохранить по новым условиям: интерфейс показывает новые лимиты, цели и ставку, сервер блокирует отправку старой версии. Две открытые сессии администратора получают `412`, если одна публикует поверх устаревшего ETag; после ознакомления можно создать новое намерение. При потере ответа UI предлагает повторить тот же запрос с тем же ключом.

Для новой программы нажать «Новая программа», указать уникальный ID (`^[a-z][a-z0-9-]{1,63}$`), условия и обоснование, проверить сводку и подтвердить создание. Программа сразу активна как версия `1`. В списке есть фильтр «Активные / Архивные / Все»; в активной карточке кнопка «Архивировать» требует обоснование и подтверждение. После архивирования новые заявки и смена продукта на архивный отклоняются `409 PRODUCT_NOT_CURRENT`; ранее созданный черновик продолжает работу с сохранённой версией, а договор, текст, SHA-256 и подпись остаются прежними. Архивную карточку и её версии можно читать, но новую версию публиковать нельзя. Если ответ потерян, повтор выполняется из сохранённой команды с прежними телом, путём, ключом и заголовками даже после reload.

Токен администратора отдельный от предпринимателя, сотрудника и внутренних API. Демоавтор аудита задаётся `DEMO_ADMIN_ID` в catalog. Политики решения, сроки и поля заявок через админ-панель не редактируются.

## Основной путь до выдачи

1. Войти предпринимателем, открыть «Кредитные продукты», выбрать «На развитие бизнеса».
2. Компания: **ООО «Демо Мастерская»**. Сумма **1 000 000 ₽**, срок **12 мес.**, цель **оборотные средства**. Месячная выручка **1 000 000 ₽**, расходы **500 000 ₽**, текущие платежи **20 000 ₽**.
3. Создать черновик. При необходимости изменить и сохранить параметры. Отметить оба согласия, нажать «Проверить и отправить», затем подтвердить отправку.
4. Дождаться предложения, нажать «Принять предложение» и подтвердить. После обработки откроется полный текст договора.
5. Прочитать договор, отметить согласие и нажать «Подписать договор». Дождаться **«Выдача подтверждена» / DISBURSED**. Отправка команды сама по себе не означает завершение выдачи.
6. Открыть «История и версии»: доступны переходы и неизменяемый снимок данных версии 1.

## Остальные сценарии

Каждая строка — новая заявка с параметрами основного пути, кроме явно измененных полей.

| Сценарий | Что изменить | Что проверить |
| --- | --- | --- |
| Кредитный отказ | Компания «Демо Просрочка» | REJECTED с причиной текущей просрочки; это бизнес-результат |
| Дозапрос проверки | Компания «Демо Нужны сведения» | NEEDS_INFO: заполнить «Описание бизнеса», отправить сведения; dataVersion=2, повторное рассмотрение |
| Дозапрос первичной валидации | Цель REFINANCING / рефинансирование | Запрошен «Рефинансируемый долг, ₽»; указать 1 000 000 и отправить |
| Дозапрос скоринга | Месячные расходы 0 ₽ | Запрошено пояснение выручки/расходов; заполнить текст и отправить |
| Встречное предложение | Выручка 600 000 ₽, расходы 500 000 ₽ | Вместо 1 000 000 ₽ / 12 мес. предложены 750 000 ₽ / 36 мес. Можно принять либо изменить условия |
| Изменение условий | В готовом предложении выбрать «Изменить условия», например 700 000 ₽ / 36 мес. | Повторное рассмотрение, dataVersion=2, прежний снимок остается в истории |
| Ручной анализ | Компания «Демо Ручной анализ», срок 36 мес., текущие платежи 160 000 ₽ | MANUAL_REVIEW с оценкой 550. Сотрудник открывает очередь, выбирает дело, допустимые оцененные условия и пишет обоснование от 10 символов; APPROVE приводит к предложению |
| Спорные факты | Компания «Демо Спорные данные» | MANUAL_REVIEW без завершенного скоринга; APPROVE недоступен. Требуется уточнение фактов/данных или обоснованный отказ |
| Отмена | Создать черновик и отменить с причиной | CANCELLED, дальнейшая отправка невозможна |

Staff-очередь: `/staff/manual-reviews`. Сотрудник также может отказать с обоснованием, запросить сведения или исправить данные. После изменения данных проверяется новая версия, старые результаты сохраняются. Клиент видит итог после обновления карточки.

Срок ответа на дозапрос и подписи — 72 часа, принятия предложения — 168 часов. Быстрое истечение срока и сетевые сбои отдельно проверяются тестами компонентов; в реальном UI нет тестовых переключателей времени/сбоев. Нельзя применять `window.__MOCK__` при выключенных моках.

## HTTP-проверка

```bash
curl -fsS http://localhost:8080/health/live
curl -fsS http://localhost:8080/config.js
curl -fsS -H 'Authorization: Bearer demo-customer-only' http://localhost:8080/api/v2/companies
python3 scripts/smoke_local.py
```

Smoke-скрипт создает синтетические заявки в текущей БД и проверяет настоящие HTTP-вызовы через gateway: выдачу/договор/историю, отказ, три дозапроса, встречное предложение, смену условий, ручное одобрение, запрет APPROVE при спорных фактах и отмену. Заявки остаются в интерфейсе для изучения. Подробные ручные HTTP-запросы: `contracts/examples/requests.http`; base URL для них — `http://localhost:8080/api`.

## Управление

```bash
# Логи API/оркестратора:
docker compose -p alfa-local logs --tail=100 applications worker
# Повторный запуск без пересборки:
docker compose -p alfa-local up -d --wait
# Остановка, данные сохраняются:
docker compose -p alfa-local down
```

Данные хранятся в volume `alfa-local_postgres-data`. Не удаляйте volume, если нужно сохранить заявки. Техническая ошибка отображается отдельно от кредитного статуса; изучите `technicalError`, логи worker и доступное действие повтора.

## Расширенные браузерные E2E

После запуска стека:

```bash
npm --prefix frontend ci
npm --prefix frontend run test-e2e:real
```

Отдельный набор со стабами: `npm --prefix frontend run test-e2e`. [Матрица покрытия и границы проверок](../frontend/e2e-real/README.md) описывает клиентские, staff-сценарии, конкуренцию, восстановление и изоляцию тестовых заявок. Оба набора сохраняют HTML-отчеты и traces в отдельных каталогах `frontend/playwright-report/{real,mock}` и `frontend/test-results/{real,mock}`.

## Изолированная проверка общего staff-реестра

Из корня checkout (Docker Compose с поддержкой !override, Python 3):

```sh
python scripts/staff_registry_stack.py --project alfa-staff-it-review --port 18085
E2E_BASE_URL=http://127.0.0.1:18085 npm --prefix frontend run test-e2e:real
python scripts/staff_registry_stack.py --project alfa-staff-it-review --down
```

На Windows переменные задаются через `$env:E2E_BASE_URL='http://127.0.0.1:18085'`; `PLAYWRIGHT_CHROMIUM_EXECUTABLE` может указывать на установленный Edge. Node 22.22.1, Java 21, Gradle 8.14.3. Скрипт использует закрепленный Gradle/JDK21 builder с кешем зависимостей и исходный runtime Dockerfile; он только упаковывает production-код, unit/integration тесты запускаются отдельно. Временные Dockerfile удаляются. Имена проекта ограничены префиксом alfa-staff-it-, отдельные сеть/БД/volume/порт, seed и часы штатные; HTTP-стабов нет.

После интеграции origin/main (451f5ab) общий infra/migrate.sh обнаруживает applications/003 и catalog/003 автоматически. Изолированный профиль staff-registry использует тот же общий мигратор, отдельный вызов applications runner удален. Индекс реестра и жизненный цикл программ применяются владельцами схем; runtime-пользователи сохраняют только DML. Для обновления обычного Compose повторно запустите штатный migrate перед API/worker.
