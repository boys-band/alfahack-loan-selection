# Спецификация frontend

Desktop веб-приложение проводит предпринимателя от выбора продукта до моделируемой выдачи кредита. Сотрудник видит очередь ручного рассмотрения и принимает обоснованные решения. Данные и доступность действий определяет backend; frontend отображает их и отправляет команды API v2.

Спецификация описывает предстоящую реализацию. Основание: [требования](../REQUIREMENTS.md), [бизнес-модель](application-state-model.md), [workflow](workflow.md), [архитектура](architecture.md), [общие правила HTTP](../contracts/README.md).

## Границы

- Обязательны клиентский desktop-путь и минимальный экран сотрудника. Все основные операции выполняются внутри приложения.
- Backend-интеграция — только публичные API applications и catalog через gateway: `/api/v2/*`. Внутренние verification/decision/agreements/disbursement и их токены недоступны браузеру.
- Скоринг, состояние заявки, время принятия, авторство, сроки и сумма выдачи определяются сервером. Формы не позволяют прислать эти значения вместо серверных.
- Договор и подпись, счета и выдача моделируются. Регистрация компании, реальная ЭП, платежи, OCR, загрузка документов, чат и посткредитное обслуживание в этот объем не входят.

## Роли и вход

Расширение административного UI: отдельная роль «Администратор продуктов» входит демотокеном и работает на `/admin/products` и `/admin/products/:id` через публичный API catalog. Его права не совпадают с ролью сотрудника рассмотрения. Экран сравнивает значения до/после и требует подтверждения публикации новой версии; старые версии остаются доступны. Административные команды сохраняют точный `If-Match`, ключ и тело для повтора после reload; `412` сохраняет форму и требует нового подтверждения.

В карточке программы кнопка «Отменить изменения» возвращает поля и цели к загруженным условиям, очищает причину изменения и сообщения об ошибках формы. Отмена выполняется локально, после неё можно уйти без предупреждения о несохранённых правках условий. Пока выполняется запрос либо не разрешена сохранённая команда публикации/архивирования, кнопка недоступна. Опубликованные версии сохраняются.

Экран демодоступа `/demo-access`: выбор роли «Предприниматель» / «Сотрудник» / «Администратор продуктов» и ввод соответствующего синтетического токена. Над формой отображаются тестовые токены по ролям для текущего режима: HTTP-стабов либо стандартного локального стенда; для изменённой конфигурации есть пояснение обратиться к организатору. Новый backend endpoint логина не требуется. Первый запрос компаний, staff-очереди или admin-каталога проверяет доступ. Экран отличает непринятый токен (401), неподходящую роль (403) и техническую недоступность; текст ошибки сервера не выводится. Исправление ввода или смена роли очищает ошибку; во время проверки роль и токен менять нельзя.

Токен передается как Bearer и хранится в sessionStorage до выхода/закрытия сессии. Роль выбирает навигацию, а права проверяет сервер. Токены не помещаются в URL, логи и сообщения об ошибках. `INTERNAL_API_TOKEN` не входит в сборку или конфигурацию браузера.

Клиент видит свои компании и заявки. Сотрудник работает через staff API и разрешенные GET заявок/истории/договора; клиентские команды принятия/подписи ему не показываются. Смена роли очищает кэш данных и отделяет незавершенные команды разных демоличностей.

## Экраны и маршруты

`/` переводит вошедшего клиента в `/applications`, сотрудника — в `/staff/manual-reviews`, без сессии — в `/demo-access`. Прямые ссылки и перезагрузка любого маршрута должны работать.

| Маршрут | Содержание | Основное действие |
| --- | --- | --- |
| `/products` | Активные продукты, суммы/сроки/цели/ставки и ограничения | Выбрать продукт |
| `/applications` | Заявки, компания, статус/вложенный этап, сумма, обновление, следующее действие | Открыть или создать заявку |
| `/applications/new` | Выбор своей компании и продукта, параметры и финансовые данные | Создать черновик |
| `/applications/:id` | Общая карточка заявки; содержимое меняется по состоянию | Действие из `availableActions` |
| `/applications/:id/history` | История по sequence: переходы, версии, инициатор, время и причина | Открыть сохраненную версию |
| `/applications/:id/versions/:dataVersion` | Неизменяемый снимок отправленных данных и источник изменения | Вернуться к актуальной заявке |
| `/applications/:id/agreement` | Полный текст договора, условия, статус и срок подписи | Подписать при доступности SIGN |
| `/staff/manual-reviews` | Дела: applicationId, dataVersion, причина, состояние и время | Открыть актуальное дело |
| `/staff/applications/:id` | Заявка, факты/расхождения, оценка/кандидаты, дело и форма решения | Действие из `manualReview.allowedActions` |

Списки заявок и дел используют `limit`, непрозрачный `cursor` и `nextCursor` из API. Не выдумывать total/count, серверную сортировку и фильтры, которых нет в контракте. Номера сохраненных версий берутся из текущей dataVersion и истории; архивной версии черновика 0 нет.

## Общая карточка заявки

Верхняя часть: компания, продукт, номер заявки, статус с понятной русской подписью и nextActionHint. Основная область: текущие сведения/результат. Справа или ниже: доступное действие, срок, предупреждение о техническом ожидании. История и договор доступны отдельными ссылками при наличии данных.

Предприниматель видит результат рассмотрения и условия предложения. При отказе показывается общее сообщение без конкретных банковских причин. Баллы, факторы риска, результаты внутренних проверок и обоснования сотрудника отображаются только сотруднику, включая историю и сохранённые версии; JSON-структуры запросов/ответов, технические коды, RequestId и хеши не выводятся в интерфейсе. Скоринг не изображается как вероятность одобрения. Нет искусственного процента готовности и обещания точного времени рассмотрения.

| status / reviewStage | Что видит клиент | Поведение |
| --- | --- | --- |
| `DRAFT` | Сохраненные/незаполненные поля, сохранность изменений | Редактирование, сохранение, согласия и отправка |
| `SUBMITTED` | «Заявка отправлена» | Ожидание приема в обработку |
| `VALIDATION` | «Проверяем данные заявки» | Ожидание первичной проверки |
| `IN_REVIEW / ENRICHMENT` | «Получаем и сверяем сведения» | Объяснение выполняемого этапа |
| `IN_REVIEW / SCORING` | «Оцениваем риск и условия» | Отдельный этап после обогащения |
| `NEEDS_INFO` | Конкретные требования, причина, срок | Форма ответа на текущий дозапрос |
| `MANUAL_REVIEW` | «Заявку рассматривает сотрудник» | Причина ожидания без обещания одобрения |
| `OFFER_READY` | Запрошенные/предложенные сумма и срок, ставка, платеж, причины и срок | Принять конкретное предложение либо изменить условия |
| `OFFER_ACCEPTED` | Зафиксированные условия; «Готовим договор» | Ожидание документа, прежний срок предложения больше не используется |
| `AWAITING_SIGNATURE` | Договор, версия, срок signBy и согласие на подпись | Подпись точного документа |
| `SIGNED` | Подписанный договор и состояние проверки счета | При NEEDS_CORRECTION — причина и выбор другого своего счета |
| `DISBURSING` | «Подтверждаем зачисление» | Не предлагать повторную выдачу или изменение реквизитов |
| `DISBURSED` | Подтвержденные сумма, счет, время и номер операции | Финальный результат без новых команд по этой заявке |
| `REJECTED` | Общий результат отказа без внутренних причин и оценок | Просмотр результата/истории, создание новой заявки |
| `CANCELLED` | Подтвержденная отмена | Просмотр истории, создание новой заявки |
| `EXPIRED` | Причина истечения INFO/OFFER/SIGNATURE и срок | Просмотр истории, создание новой заявки |

Отмена показывается только при `CANCEL` в availableActions; перед командой — подтверждение и причина. В гонке с подписью после 202 текст «Проверяем возможность отмены», пока сервер не подтвердит исход. Подписанный договор не показывать отмененным по одному факту клика.

Технический сбой — отдельное сообщение поверх сохраненного бизнес-статуса с этапом, причиной и возможностью повтора. RETRY_PROCESSING показывать только при серверном разрешении. Дозапрос и необходимость поправить счет не оформлять как технические сбои.

Кнопки клиента разрешаются только списком `availableActions` и проверкой срока; сам status не заменяет это разрешение:

| Действие API | Кнопка | Команда |
| --- | --- | --- |
| `EDIT` | Сохранить черновик | updateDraft |
| `SUBMIT` | Отправить заявку | submitApplication |
| `PROVIDE_INFO` | Отправить сведения | provideInformation |
| `CHANGE_TERMS` | Изменить условия | changeTerms |
| `ACCEPT_OFFER` | Принять предложение | acceptOffer |
| `SIGN` | Подписать договор | signApplicationAgreement |
| `CANCEL` | Отменить заявку | cancelApplication |
| `UPDATE_PAYOUT_ACCOUNT` | Изменить счет | updatePayoutAccount |
| `RETRY_PROCESSING` | Повторить обработку | retryProcessing |

## Формы и подтверждения

При создании заявки из каталога ссылка «Кредитные продукты» возвращает в каталог, сохраняя это направление после перезагрузки формы. При входе из списка заявок или по прямой ссылке возврат ведёт в «Мои заявки». Уход с изменённой формы требует подтверждения потери несохранённых данных.

Окно подтверждения отправки заявки располагается по центру видимой области. Сохранённые условия, финансы и дополнительные сведения отображаются с русскими подписями без JSON и внутренних имён полей. Длинное содержимое прокручивается внутри окна; кнопка отправки остаётся доступной. Крестик и Escape закрывают окно и возвращают фокус на кнопку, открывшую подтверждение.

| Форма | Поля и правила |
| --- | --- |
| Черновик | companyId; productId + productVersion; amountRub; termMonths; purpose; месячные выручка, расходы и действующие платежи; дополнительные сведения. Компания выбирается из своих, цель — WORKING_CAPITAL/EQUIPMENT/REFINANCING с русскими подписями |
| Финансы | `monthlyRevenueRub`, `monthlyExpensesRub`, `existingMonthlyDebtPaymentsRub`; целые рубли, ноль допустим по схеме. Пустое поле не превращается в ноль |
| Дополнительные сведения | businessDescription, revenueExplanation, refinancedDebtRub; обязательность зависит от текущих требований и сценария |
| Отправка | Две отдельные непредустановленные галочки personalDataConsent и creditBureauConsent; submit передает оба true. До отправки показать итоговые сведения |
| Дозапрос | requirements[].path/message сопоставляются понятным полям; informationRequestId фиксирован. Отправляется changes, а не полная Application |
| Смена условий | Новая сумма/срок или пара productId/productVersion; требуется реальное изменение. Показать, что начнутся новые проверки и прежнее предложение перестанет быть актуальным |
| Принятие | Сверка предложенных условий и срока; передаются offerId, offerVersion, dataVersion из актуального ответа |
| Подпись | Прочитать полный документ, явно отметить consent; передаются agreementId, documentVersion и documentSha256 именно показанного документа. Это моделируемая подпись |
| Поправка счета | Выбрать свой счет из публичного списка accounts компании. Передается settlementAccountId; подписанные кредитные условия не редактируются |

Точные типы/диапазоны/длины задает [schemas.yaml](../contracts/schemas.yaml). PATCH черновика: пропуск не меняет поле, null очищает, вложенный объект заменяется целиком. DataChanges после отправки не содержит null; productId и productVersion меняются вместе, additionalInfo заменяется целиком. При заполнении изменений сохранять соседние значения заменяемого объекта.

Автосохранение не обязательно: явная кнопка «Сохранить черновик» достаточна. Показывать несохраненные изменения, предупреждать при уходе и не затирать их фоновым GET. Неизвестный путь дозапроса отображается с сообщением как непокрытое требование, а не молча отбрасывается или исполняется как произвольный доступ к объекту.

В поле цели кредита доступны только `purposeCodes` выбранной версии продукта. При создании до загрузки условий продукта поле цели и сохранение недоступны; смена продукта требует заново выбрать цель. Черновик сверяется с текущими активными условиями; дозапрос и уточнение сотрудника используют сохранённый снимок продукта, смена условий — выбранную версию программы. Неподходящая прежняя цель сбрасывается при смене продукта либо помечается в существующем черновике и требует исправления. Пустая цель в неполном черновике по-прежнему допустима.

Если программа изменилась после создания черновика, показывать уведомление с новой версией, суммой, сроком, ставкой и целями. Отправка доступна после проверки данных и явного сохранения черновика по новым условиям. Перед открытием подтверждения повторно читать текущую программу; сервер дополнительно проверяет её при submit. При недоступном catalog сохранение и отправка блокируются, введённые данные сохраняются. Уже отправленные заявки не переводятся на новые условия автоматически.

Текст документа `text/plain` отображается с сохранением переносов и экранированием. Подписывать документ, подмененный после открытия, нельзя: после обновления версии/хеша потребуется повторное ознакомление/согласие.

## Рабочее место сотрудника

Очередь запрашивается у applications, а не напрямую у decision. Карточка загружает Application и актуальное ManualReviewCase. Сотрудник видит исходные/подтвержденные факты, расхождения, причины передачи, текущие assessment/evaluatedTerms, факторы риска и историю версий. Факты и оценённые варианты кредита сопоставляются в таблицах, различия выделяются текстом. Вклад факторов риска показан диаграммой в баллах из серверной оценки; новые кредитные расчёты в UI не выполняются.

| Действие | Форма |
| --- | --- |
| `APPROVE` | Выбрать termsId из оцененных допустимых кандидатов и обоснование. Без завершенной оценки/подтвержденных фактов кнопка отсутствует |
| `REJECT` | Обоснование; отдельное подтверждение отказа |
| `REQUEST_INFO` | Непустой список понятных требований с JSON Pointer и сообщениями; обоснование |
| `AMEND_DATA` | Изменения полей и/или подтвержденные факты по verificationId своего дела; обоснование. Предупредить о новой версии и повторных проверках |

Обоснование — 10–2000 символов. Отправлять `StaffReviewActionRequest`: без staffId/actionId, с обязательными nullable полями и requirements=[] у действий без дозапроса. Автора и actionId устанавливает applications. Нельзя использовать внутренний ManualReviewActionRequest из decision.

Доступность банковских действий — пересечение роли сотрудника, актуального MANUAL_REVIEW и manualReview.allowedActions. `Application.availableActions` является клиентской проекцией даже в staff GET и не дает сотруднику клиентских прав. При смене версии/закрытии дела форма перестает быть исполнимой; уже введенное обоснование не отправляется в другое дело автоматически.

### Конкуренция и повторы

- У каждой намеренно новой POST/PATCH-команды новый Idempotency-Key. До отправки сохранить метод, конкретный путь, точное тело либо отсутствие тела, If-Match и ключ в журнале незавершенных команд sessionStorage своей демоличности. Повтор того же намерения сохраняет все эти значения после таймаута и перезагрузки.
- PATCH и команды существующей заявки требуют If-Match — дословный ETag последнего GET/актуального представления. ETag не вычисляется из version в браузере. Если данных списка недостаточно для получения ETag, перед командой выполнить GET карточки. Staff action тоже использует ETag Application.
- Новое действие в форме нельзя отправить, пока исход прежней команды этой заявки не разрешен. Двойной клик не создает новый ключ. GET-опрос не заменяет сохраненное тело/ETag неразрешенной команды.
- После сетевой ошибки сначала перечитать карточку и затем при необходимости повторить исходную команду с прежним ключом/телом/If-Match. Не объявлять отказ или успех по одному таймауту. После 202 показывать прием команды и перечитывать заявку до фактического исхода; 200/201 и повтор успешного ответа также сопровождаются обновлением карточки.
- Сохраненный ответ повтора может быть старее текущего GET: не откатывать экран на его status/version. Устаревшие ответы предыдущей роли/карточки/запроса не применяются.
- 412: сохранить введенные данные, перечитать карточку, показать изменение и предложить заново подтвердить действие. Новое намерение получает новый ключ и ETag; автоматически переписывать If-Match прежнего ключа нельзя. Аналогично не повторять смысловое действие молча после DEADLINE_EXPIRED/OFFER_NOT_CURRENT/INVALID_STATE.
- 409 IDEMPOTENCY_IN_PROGRESS и 429 учитывают Retry-After. IDEMPOTENCY_CONFLICT — ошибка согласованности команды, без автоматического нового ключа. Неповторяемые ошибки формы/доступа не входят в бесконечный retry.

### Опрос и время

Активная обработка/processing — GET карточки примерно каждые 2 секунды без перекрывающихся запросов. При ожидании человека (дозапрос, предложение, подпись, ручное дело без обработки) — каждые 15 секунд; отдельный локальный таймер обновляет остаток срока. Финальные состояния не опрашиваются. Скрытая вкладка приостанавливает регулярный опрос, возврат фокуса сразу обновляет данные. На сетевых сбоях GET задержка растет до 15 секунд, учитывается Retry-After.

Показывать абсолютный срок с часовым поясом и оставшееся время. Для смещения часов использовать HTTP Date ответа, если он доступен; без него обратный отсчет ориентировочный. При достижении срока локально остановить действие и немедленно обновить GET; окончательное право и исход определяет сервер. ETag может измениться по времени без изменения version. Для подписи используется signBy/actionDeadline договора, а не прежний expiresAt предложения.

### Ошибки и состояния загрузки

У каждого экрана: начальная загрузка, пустое состояние, данные, обновление без исчезновения данных, ошибка с повтором. `errors[].path` связывается с полем, а общее Problem показывается рядом с формой. Вместо JSON Pointer показывается название поля; RequestId сохраняется в API-клиенте и не отображается в интерфейсе.

Сводка ошибок программы называет конкретное поле, включая идентификатор, суммы, сроки, ставку, цели и обоснование. Ошибки локальной схемы объясняют нарушенное ограничение, а известные сообщения валидации каталога переводятся на русский язык. Идентификатор программы содержит 2–64 строчные латинские буквы, цифры или дефисы и начинается с буквы.

Формы проверяют изменяемые поля во время ввода и показывают отдельные русские сообщения под каждым некорректным полем с `aria-invalid` и `aria-describedby`. После попытки отправки видны все ошибки, а фокус переходит к одному из полей, требующих исправления. Исправление одного значения снимает его ошибку, сохраняя остальные. Пустые необязательные поля черновика разрешены; в формах изменения отправленной заявки и действия сотрудника обязательные поля нельзя очищать, а в ответе на дозапрос нужно заполнить запрошенные сведения. В редакторе программы дополнительно проверяются порядок минимальной/максимальной суммы и срока, непустой набор целей и длина обоснования в символах Unicode. Невалидная форма не создаёт команду в журнале и не отправляет её в API. Серверная проверка остаётся окончательной. В общих полях заявки ошибка конкретного поля перестаёт отображаться после изменения его значения, а новая ошибка ответа снова связывается с текущим вводом.

401 возвращает к демовходу с сохранением безопасного адреса возврата внутри приложения; 403 объясняет отсутствие прав; 404 сообщает, что ресурс недоступен или отсутствует. Ошибка сети/503 не превращается в REJECTED. Полезные данные последнего успешного GET сохраняются с отметкой о неактуальности; опасные команды до разрешения ошибки не запускаются автоматически.

## Визуальные и технические условия

Desktop от 1280×720, проверочные размеры 1280×720 и 1440×900. Русский интерфейс, светлый фон, темный текст, один красный акцент основных действий, заметные состояния ожидания/ошибки. Статусы различаются текстом/иконкой, не только цветом. Обязательной мобильной версии нет.

Известные коды статусов и этапов в подсказках заявки и системных записях истории переводятся на русский язык. Статус ручного дела в очереди сотрудника также имеет русскую подпись. Авторские комментарии сохраняются дословно; исходные значения API не изменяются.

Читаемые формы с явными подписями и единицами «₽», «мес.», «%». Ставки переводятся из б.п. для отображения, серверные суммы/платежи не пересчитываются для принятия решения. Таблицы/история/договор допускают собственную прокрутку; основной экран без горизонтального переполнения.

Клавиатурная навигация, видимый фокус, связанные с полями ошибки, перенос фокуса на итог ошибки/открытый диалог, работающая клавиша Escape для закрываемых диалогов. Опрос не сбрасывает фокус и не зачитывает заново всю карточку.

SPA с типизированным клиентом; конкретный UI-фреймворк и версии фиксируются исполнителем. Runtime-конфигурация браузера содержит `API_BASE_URL` (по умолчанию `/api`) и `MOCK_API` (по умолчанию false). Внутренний HTTP-сервер контейнера — `0.0.0.0:3000`; gateway обслуживает браузер через 8080. Нужен fallback на index для UI-маршрутов, но отсутствующий asset не должен возвращать HTML с 200.

Режим моков включается явно и имеет видимую отметку. Контрактные стабы позволяют разрабатывать независимо от backend; production-сборка по умолчанию обращается к реальному API. БД и прямые подключения к сервисам из браузера отсутствуют.

Для разработки с реальным gateway настроить same-origin proxy `/api` в dev-сервере и описать адрес назначения в README. Изменение CORS или авторизации backend ради локального frontend в эту задачу не входит.

## Приемка

| Сценарий | Проверяемый результат |
| --- | --- |
| Основной путь | Продукт → черновик → согласия → обе стадии рассмотрения → принятие → договор → подпись → подтвержденная выдача |
| Три дозапроса | VALIDATION/verification/decision корректно показывают поля, срок и новую версию после ответа |
| Встречное предложение | Видна разница с запросом; принятие использует конкретный offer, смена условий запускает новый цикл |
| Ручная работа | Четыре действия сотрудника, авторство с сервера; APPROVE без оценки недоступно |
| Версии/история | Старые данные читаются без возможности редактирования; показаны причины и смена вложенного этапа |
| Три срока | На границе действия блокируются и данные обновляются; учитываются часы клиента и отдельный signBy |
| Отмена/подпись | После 202 нет преждевременной отмены; серверный победивший исход показан последовательно |
| Исправление счета | SIGNED с причиной ожидания → новый свой счет → проверка → выдача, без изменения документа |
| Технический сбой | Прежний status/reviewStage сохранен; retry соответствует серверному разрешению |
| Таймаут/перезагрузка | Та же команда повторяется с прежним ключом, телом и If-Match; лишняя заявка/подпись/выдача не появляются |
| Конфликт/двойной клик | 412 сохраняет форму и требует нового подтверждения; двойной клик и старый ответ не откатывают состояние |
| Доступ | Customer/staff не смешиваются; в bundle/сети нет INTERNAL_API_TOKEN или вызовов внутренних API |
| Навигация/сборка | Прямые URL, reload, пустые состояния и размеры desktop работают; мок явно обозначен |

Проверка UI со стабами обязательна; после готовности backend основной путь и восстановление проходят через настоящий gateway. Стабы не являются доказательством сквозной готовности продукта.

## Общий staff-реестр

Сотруднику доступны отдельные разделы «Все заявки» (`/staff/applications`) и «Ручное рассмотрение». Реестр читает только публичный `listStaffApplications` с серверными status/approvalType/limit/cursor. Параметры сохраняются в URL, смена фильтра начинает первую страницу. Таблица показывает ID, компанию/ИНН, снимок программы/версию, сумму/срок, статус, актуальное решение, даты и ссылку. Nullable-поля черновика отображаются как «—».

Карточка, история, сохраненная версия и договор имеют staff-маршруты с Role guard. Возврат сохраняет реестр/ручную очередь и параметры; прямая ссылка возвращает в реестр. Клиентские команды сотруднику не показываются. Запрос ручного дела допустим только для актуального OPEN MANUAL_REVIEW; остальные статусы не порождают служебных 404. Поздние ответы старых фильтров/сессии игнорируются. Существующие If-Match/идемпотентность/ручные guards сохраняются.
