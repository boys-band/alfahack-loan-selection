# Контракт состояний и кредитных правил v2

Источник бизнес-переходов — [application-state-model.md](application-state-model.md). Здесь зафиксировано отображение этой модели в API. `applications` — единственный владелец глобального состояния.

## Состояния

`status`: `DRAFT`, `SUBMITTED`, `VALIDATION`, `IN_REVIEW`, `NEEDS_INFO`, `MANUAL_REVIEW`, `OFFER_READY`, `OFFER_ACCEPTED`, `AWAITING_SIGNATURE`, `SIGNED`, `DISBURSING`, `DISBURSED`, `REJECTED`, `CANCELLED`, `EXPIRED`.

Только при `status=IN_REVIEW` обязательно `reviewStage=ENRICHMENT|SCORING`; во всех других состояниях `reviewStage=null`. `SCORING` не является самостоятельным глобальным статусом. `PROCESSING_ERROR` отсутствует: ошибка представлена отдельным полем.

Конечные состояния: `DISBURSED`, `REJECTED`, `CANCELLED`, `EXPIRED`. Из них нет переходов; новая потребность создает новую заявку. Дозапросы/ручное рассмотрение не объявляются техническими ошибками.

## Версии, сроки и действия

`version` увеличивается при каждом сохраненном изменении агрегата. Черновик имеет `dataVersion=0`, отправленный снимок начинается с 1. При новой версии источник изменения — `CUSTOMER_INFO`, `CUSTOMER_TERMS` или `STAFF_AMENDMENT`; предыдущие снимки, факты, оценки, дела и предложения остаются в истории. Результат старого снимка не применяется к новому.

Принятое предложение закрепляет `offerId`, `offerVersion`, `dataVersion` и неизменяемые условия. Старое предложение закрывается при смене условий/версии, отмене или истечении. Предложение от ручного решения имеет собственный ID, версия предложения в текущем протоколе всегда 1; изменение условий создает новый ID.

Сроки по умолчанию: ответ на дозапрос — 72 часа от создания; принятие предложения — 168 часов от его выдачи; подписание — 72 часа от создания договора. Поля `deadlineKind/actionDeadline` в заявке заполнены только для соответствующего ожидания. Принятое в срок предложение не истекает по старому `expiresAt` во время подготовки/подписания договора.

`availableActions` — действия клиента-владельца, вычисленные сервером по статусу и текущему времени. При чтении сотрудником это та же клиентская проекция; банковские действия перечисляет manualReview.allowedActions. После deadline действие ответа/принятия/подписи отсутствует еще до записи `EXPIRED`. ETag — непрозрачный SHA-256 текущего представления; при истечении доступности он может измениться без изменения `version`. Клиент передает полученный ETag дословно.

Действия клиента: `EDIT`, `SUBMIT`, `PROVIDE_INFO`, `CHANGE_TERMS`, `ACCEPT_OFFER`, `SIGN`, `CANCEL`, `UPDATE_PAYOUT_ACCOUNT`, `RETRY_PROCESSING`. При техническом ожидании сохраняются допустимые отмена/повтор. Сотрудник работает через отдельный staff API; допустимые банковские действия возвращаются в деле.

## Прозрачные кредитные правила

`demo-policy-v2` — синтетические правила, не реальные правила банка. Оценка риска отделена от исхода решения, ручного обоснования и условий предложения. Запрашиваемые сумма/срок/продукт проходят форматную и продуктовую валидацию перед отправкой. При свободном потоке <= 0 кредитное решение содержит стоп-причину, а не ошибку API.

Платеж: `r = annualRateBps / 10000 / 12`; `ceil(amount × r / (1 − (1+r)^(-months)))`, при нулевой ставке `ceil(amount / months)`. Decimal, не менее 28 значащих цифр. Свободный поток = месячная выручка − расходы; нагрузка = `ceil((текущие платежи + новый платеж) / свободный поток × 10000)` либо null при неположительном потоке.

Баллы: база 300; БКИ >=750 / 600–749 / <600 добавляет 250/150/0; возраст >=24 / 12–23 / <12 месяцев добавляет 150/75/0; нагрузка <=3000 / 3001–5000 / >5000 б.п. либо null добавляет 200/100/0. Диапазон 300–900; класс LOW >=800, MEDIUM 600–799, HIGH <600. Автоматическое одобрение при >=600; 500–599 — ручное; <500 — отказ.

Не допускают одобрение: неактивная компания, текущая просрочка, налоговый долг >100 000 ₽, бизнес моложе продуктового ограничения, неположительный поток, превышение продуктовой нагрузки или лимитов суммы/срока/цели. Пограничный риск сам по себе не отменяет эти ограничения. Ручное одобрение возможно при балле >=500 и отсутствии стоп-причин; условия проверяются и риск рассчитывается заново для выбранного кандидата. Исправление исходных фактов оформляется новой версией и повторными проверками.

Сначала оцениваются исходные условия. Если автоматического одобрения нет, нагрузка >3000 б.п. и отсутствуют прочие стоп-факторы, рассматриваются альтернативы: та же сумма на максимальный срок продукта, затем 75% и 50% исходной суммы на максимальный срок (целая часть рублей, не ниже минимума; дубликаты исключаются). Для каждого кандидата заново рассчитываются риск, платеж и все ограничения. Выбирается первый проходящий автоматическое одобрение; если его нет, первый допустимый кандидат с баллом 500–599 передается сотруднику; иначе отказ. В ответе сохраняются все `evaluatedTerms`, `selectedTermsId` и тип предложения REQUESTED/COUNTER. Другой продукт клиент выбирает через change-terms.

Синтетические условия дозапроса: при рефинансировании без `additionalInfo.refinancedDebtRub` первичная валидация запрашивает это поле; verification использует сценарии из seed; decision при нулевых заявленных расходах и отсутствии `additionalInfo.revenueExplanation` запрашивает объяснение до расчета. Негативные полные факты всегда доходят до оценки/решения.

## Проверка реализации

Обязательны основной путь до выдачи; все три источника NEEDS_INFO; ручное одобрение/отказ/дозапрос/правка; запрет одобрения без скоринга; проверенная альтернатива; новый продукт через change-terms; сохранность истории версий; три deadline и граница now == deadline; отмена всех разрешенных состояний; гонки отмены/подписи и истечения/принятия; сохранение бизнес-статуса при сбое; неприменение поздних результатов; исправление реквизитов в SIGNED; поиск неизвестной выдачи и отсутствие второго зачисления после перезапуска.

Фикстуры и HTTP-примеры находятся в `contracts/examples`. Время и сбои подменяются в тестах/стабах; клиент не передает тестовые переключатели.
